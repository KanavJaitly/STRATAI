## P11-Q1: the recommendation source while the gates are unmet → option (b)

There are two sources, tried in a fixed order and never mixed:

1. **The P6-M7 engine, unchanged.** `ml.playoffs.service.pick_list` runs for the selecting seed's next turn at the
   record's current state, with the same dependencies the locked `POST …/alliance-selection/pick-list` uses. If it
   returns, its ranking is served with the status it gives (`validated_playoff_success`, with its scope reasons). No
   gate is lowered, and no gate is read anywhere except through the engine.
2. **The fallback rule P11-FB1**, used only when the engine refuses. The engine's refusal (code and message) is
   always served with the fallback, so nobody can mistake one source for the other.

**P11-FB1 (frozen here, 2026-11-04, before implementation):**
- **Ordering:** the P5-M4 event-analysis ordering (`ml.views.event_analysis.analyze_event`) at the event's
  selection moment (`ml.playoffs.service.event_selection_moment`), under its frozen policy: raw EPA before the switch
  point, and M5 v2 after it. It uses the served EPA source and the pinned ranking model. If the analysis refuses (for
  example `model_not_loaded`, or EPA source missing or incomplete), recommendations are withheld with that reason.
  There is no further fallback.
- **Candidates:** the record's available pool (the event's rules applied to the recorded state), minus the selecting
  alliance's own members. An available team with no position in the ordering is listed separately as
  `unranked_available` and is never placed among the recommendations.
- **Primary:** the first candidate in the ordering.
- **Backups:** the next `B` candidates in the ordering. `B = max(3, m)`, where `m` is the number of other alliances'
  picks before the selecting alliance's next turn. The list is capped at the candidates that exist. If at most `m`
  teams are picked before that turn and nobody declines, at least one listed team is still available when the turn
  comes.
- **Whose recommendations:** the recommendations belong to the alliance the workspace's team is on, or is projected
  to captain under the rules and ranks. If that alliance has no remaining turn, or the team is neither on nor
  projected to captain an alliance, recommendations are withheld with `team_not_selecting`.
- **Status:** `not_validated`. The reason says the ordering is a team-strength ordering (P5-M4, with its own
  status). It is not validated as a pick recommendation and gives no P(win event). The fallback shows no
  probability.
- **Movement:** each response explains why a candidate moved, as fixed-template text derived only from the record
  ("T was picked by alliance 3; S is now first"). No free text is generated, and no LLM is used.
- **Not allowed:** P11-FB1 never feeds the P6-M7 engine, the draft model, or any gate. It is not P6-Q6's draft
  model, and it does not change it.

## P11-Q2: who records draft actions → a configurable permission, off by default

- A new configurable permission, `alliance_selection_record` ("Recording live alliance-selection actions"), is added
  to `workspaces/permissions.py` `CONFIGURABLE_PERMISSIONS` and to the `workspace_role_permissions` CHECK constraint
  (migration 0013).
- Administrators always hold it. It is NOT in `DEFAULT_GRANTS` for strategy or scouter, so recording is
  administrator-only until an administrator grants it to a role in the Permissions tab.
- It governs start, append, undo, correct, close and reopen.

## P11-Q3: the recalculation time target → ≤ 2 s at p95

- **Measured:** the time from a recorded action being committed to a recommendation response for the new record
  sequence, at an event whose features and ordering are already computed (the warm path).
- **Reported separately:** the first (cold) computation for an event, which builds every team's features. The page
  requests recommendations as soon as a draft starts, so the cold cost is paid before picks begin.
- If the P6-M7 engine ever serves (all gates passed), its runtime counts against the same target and is measured
  then. This target does not change the engine.

## P11-Q4: who sees the live board and the picklist → the existing `alliance_selection` permission

- Reading a draft record, its state, history and recommendations requires `alliance_selection`. Administrators
  always hold it. The strategy role holds it by default; scouters hold it only if granted.
- Recording additionally requires `alliance_selection_record` (P11-Q2).

## Implementer decisions (ordinary engineering, recorded for traceability)

- **Updates reach other devices by polling** (every 2 s while a draft is open and the page is visible), not by server
  push. The deployment (Render) and Phase 12's local mode need no extra infrastructure for polling.
- **Missing ruleset.** When the season has no approved ruleset for the event, an administrator starting the record
  enters the alliance count, the picks per alliance and the decline, captain and backup rules from the event. These
  are stored raw and attributed (`source: manual_entry`), never guessed, and the record says it uses them.
- **Draft configuration is state, not a draft event.** The latest `configure` entry governs, and replay re-validates
  every draft action against it.
