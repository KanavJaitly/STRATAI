## ✅ Phase 2 Done-Criterion Validation (2026-07-25)

Phase 2's done criterion — *"manually spot-checked against known real results"* — is **satisfied**.
The full 2024 season was synced and the stored data compared by hand against
thebluealliance.com using `scripts/spot_check.py`. **Zero discrepancies:** every score,
winner, and roster matched exactly.

Coverage was deliberately chosen to hit every match type and every edge case the
canonical model has to represent:

| Checked | Why this case | Result |
|---|---|---|
| `2024mil_sf13m1` | Double elimination, **113–113 tie** broken on tech fouls with red awarded the win — the hardest winner-attribution case in the schema | Scores, winner, and both rosters exact |
| Both `2024cmptx` Einstein finals | Championship finals; rosters drawn from division winners, so it also verifies cross-event load ordering | Exact |
| Team **2056**, full 2024 season | Six events — verifies per-team history and event structure across the whole season, not just one event | All records and event structure correct |
| `2024casj` qm1 / qm30 / qm53 | Ordinary qualification matches, including an **88–5 blowout** (wide score margin) | Exact |

The comparison is human-run by design: `scripts/spot_check.py` prints canonical rows in
TBA's own layout and deliberately emits **no pass/fail verdict**, because an automated
comparison would re-implement the pipeline's normalization and agree with it by
construction. See `docs/data_pipeline.md` §8.3.

Not covered by this validation: `team_event_stats` (EPA), which is still empty — see the
open Statbotics item under Known Issues.

**Phase 2's other done criterion — *"live-event polling works without manual triggering"* —
is satisfied as of 2026-08-01** by `watch_event` / `--watch EVENT_KEY`. It cannot be
validated against a live event out of season, so what was validated instead is everything
that *can* be: the loop's control flow, deterministically and offline (44 tests, injected
clock/sync/progress), the stop-condition query against real canonical rows, and one live
smoke run against the finished `2024casj` — which polled, found everything already synced
(`landed` all zeros, a true no-op), detected `finals complete - 93/93 matches, 3/3 finals
played`, took its settle poll, and exited 0. A second run against a nonexistent event key
gave up after its configured consecutive failures and exited 1 rather than looping forever.

## 📐 Key Design Decisions Log

| Date | Decision | Rationale |
|---|---|---|
| 2026-07-23 | **Re-keyed canonical layer to `team_number`** (`0005_canonical.sql`) | `0001` had keyed teams on `team_key` TEXT (`"frc1114"`), but M6 staging strips the prefix to `team_number` INT. Tables were empty, so drop-and-recreate lost no data. Confirmed with Kanav. `events`/`matches` left untouched (already compatibly keyed). |
| 2026-07-23 | **Kept `match_teams` junction** (not `int[]` arrays) | True FK integrity on roster membership — arrays can't enforce it. Junction already existed in `0001`. |
| 2026-07-23 | **`team_event_stats` sourced from Statbotics (M5)** | Added `StagingTeamEventStats` + `normalize_statbotics_team_event_stats` so the M7 loader is exercised end-to-end, not just against hand-built rows. `epa_endgame` nullable (Statbotics may not provide it). |
| 2026-07-24 | **Watermark = highest promoted `raw_source_payloads.id`**, per `(source, object_type, event)` | Landing already dedups identical payloads, so an unchanged object lands no new row and nothing sits above the watermark — a re-sync's staging/serving stages are true no-ops, not deduplicated work. No new schema needed; `0003`'s UNIQUE `(source, object_type, scope_key)` was already the right key. Confirmed with Kanav. |
| 2026-07-24 | **`0006_pipeline_run_scope.sql`: nullable `scope_key` + `stage_counts` JSONB on `pipeline_runs`** | `0003` gave `pipeline_runs` no scope column, so runs against different events were indistinguishable and unreconcilable against watermarks. Purely additive, rollback is `DROP COLUMN`. Confirmed with Kanav. |
| 2026-07-24 | **Watermarks advance at exactly one point** — after serving succeeds | Guarantees no failure leaves a corrupt watermark. Safe to repeat a partially-completed run because every canonical write is an upsert. A failed run is recorded as `failed` and the exception re-raised, never swallowed. |
| 2026-07-24 | **Contiguous-prefix watermark advance on validation failure** | An invalid payload is skipped + recorded, and the watermark stops short of it, so it is retried on later runs instead of permanently skipped — one bad record never blocks an event's good records. Tradeoff: a permanently-malformed record is re-read every run (idempotent, cheap). Confirmed with Kanav. |
| 2026-07-24 | **Roster backfill in extraction** | TBA's event team list and match schedule are separate endpoints with no guarantee they agree; a rostered team with no `teams` row fails the whole load on the `match_teams` FK. Missing teams are fetched individually before landing. Confirmed with Kanav. |
| 2026-07-24 | **Additive client methods** (no M3/M5 signature changes) | `TBAClient.fetch_event` (single event, vs. downloading a whole season) and `fetch_event_teams` (one request, vs. ~40 `fetch_team_info` calls). Plus `city`/`state_prov`/`country` on `EventSummary` — see tech debt below. |
| 2026-07-24 | **Watermarks scoped per event, including for teams** | A team attending two events is tracked independently under each, so one event's run can never advance another's progress. Cost is one idempotent re-upsert of that team per event. |
| 2026-07-24 | **Lineage as a separate `canonical_lineage` table**, not a `source_payload_id` column on the canonical tables | Keeps the `0001`/`0005` schema and the M7 repository completely untouched, and makes lineage an append-only *history* (every payload version an entity was built from, plus the run that promoted each) instead of a last-writer pointer that can't represent multi-source entities. Confirmed with Kanav. |
| 2026-07-24 | **Severity is the reject/allow policy** — `error`/`critical` reject, `warning` records and loads | Errors are records that are meaningless or unloadable (negative score, W/L/T contradicting its own total, end date before start, reference that won't exist). Everything judgemental is a warning: a plausibility rule that discards real data is worse than no rule, since FRC scoring changes every season and today's generous ceiling will eventually be exceeded by a real match. Confirmed with Kanav. |
| 2026-07-24 | **One rejection mechanism, not two** | A fatal quality issue takes the identical path in `stage_batch` that an M8 validation failure takes: skipped, watermark held short of it, retried next run. M9 changes to M8 are additive only (default-empty `StagedBatch.issues`/`.lineage`, optional `context` param, optional `sync_event` collaborators). Confirmed with Kanav. |
| 2026-07-24 | **`ON DELETE CASCADE` on `data_quality_issues`** (incl. redefining `0003`'s run FK) | Once issues and lineage reference runs and raw payloads, deleting either — which integration teardown does — fails on a foreign-key violation. Expressing the cleanup in the schema beat editing M8's test teardown, and it's semantically right: an issue is a subordinate record of the run and payload it describes. Lineage's run FK is `SET NULL` instead, since provenance stays true even if the run record is gone. Confirmed with Kanav. |
| 2026-07-24 | **Issues written before the load, lineage after** | A failed run's quality evidence is exactly when it's wanted, so issues must not depend on the load succeeding; a lineage row asserts a canonical row exists, so it must. |
| 2026-07-24 | **One `data_quality_issues` row per detection**, not per distinct problem | A payload that stays invalid is re-detected every run (the watermark deliberately holds short of it). Collapsing detections would lose the answer to "how long has this been broken", which is what the `resolved`/`resolved_at` columns exist to support. |
| 2026-07-24 | **Rejected: checking `epa_total` against `epa_auto + epa_teleop + epa_endgame`** | Statbotics doesn't document those as summing exactly, so any tolerance would be invented statistics generating false alarms about real data. |

Re-recorded from team **1678** (Citrus Circuits), which did attend. Keeping the event key means the filename and every reference to it (`tests/`, `docs/`, `data/clients/statbotics.py`) stays valid. |
| 2026-08-01 | **TBA's `-1` unplayed score is resolved in the normalizer, never by relaxing the quality check** | TBA publishes a not-yet-played match with `score: -1` on both alliances (plus `winning_alliance: ""`, null `actual_time`/`score_breakdown`). The quality layer rejected it as a fatal "negative score", so on the full 2024 season 2 matches never loaded — but during a **live** event that is *most of the schedule*, and live in-event sync is a core project goal. The obvious fix (downgrade the negative-score rule to a warning) is a trap: `_derive_winning_alliance` compares the two `-1`s, finds them equal, and returns **`"tie"`** — so relaxing the check alone would have silently loaded every unplayed match as a tie that never happened, corrupting exactly the win/loss data Phase 3 is built on. The sentinel is therefore resolved where the raw payload is interpreted (`_alliance_scores` in `data/staging/normalizer.py`) into a NULL score, which makes the winner derivation's existing `is not None` guard return NULL on its own. `score < 0` stays **fatal**, so a genuinely corrupt score is still rejected. Confirmed with Kanav. |
| 2026-08-01 | **A one-sided sentinel nulls both scores and emits a warning** | A match cannot be half-played, and a `NULL`/`30` row is uninterpretable downstream, so a sentinel on either alliance is read as "the whole match is unplayed". That preserves the invariant that `score_red` and `score_blue` are always both NULL or both set — which is what makes `score IS NULL` a reliable "not played yet" test for Phase 3. Discarding a posted score is not silent, though: the anomaly is a `warning`, per severity-as-policy (the record is still a real scheduled match, and the reading is an interpretation, not a certainty). Because normalization deliberately erases the asymmetry, the check has to see the raw payload — hence the optional `raw_payload` kwarg on `check_entity`, which mirrors the existing optional `context` exactly: a fact the caller did not supply is skipped, never guessed at. Confirmed with Kanav. |
| 2026-08-01 | **`frc0` is resolved to an *empty* roster, not to team 0** | TBA publishes a not-yet-assigned roster as `["frc0","frc0","frc0"]` on both alliances. Team 0 does not exist, so the sentinel had to become an absence, not a value — the same principle as the `-1` fix, applied to a different field (absent score → NULL; absent roster → no `match_teams` rows). Keeping the placeholder as team 0 was rejected on three counts: there is no `teams` row for 0, so the referential check would reject the match anyway (trading one rejection for another); `match_teams` is unique on `(match_key, team_number)`, so three `frc0`s would collapse to one row regardless; and it would assert to Phase 3 that some robot played. An empty alliance was **already** a legitimate canonical state — M9 deliberately does not flag one, since playoff brackets are published before alliances are selected — so this fix stores something the model already understood rather than inventing a representation. Confirmed with Kanav. |
| 2026-08-01 | **The `frc0` exclusion is surgical: identity comparisons only, never the rule itself** | The two roster rules (`a team cannot appear twice on one alliance`, `a team cannot be on both alliances`) are exactly right for a real team and must keep rejecting genuine corruption — they are the only checks in the validator that read a team key as an *identity* rather than a string, which is precisely why the sentinel breaks them. So `frc0` is excluded from the two identity sets and nothing else changes: `["frc1114","frc1114","frc0"]` is still rejected, and a real team on both alliances is still rejected, both test-pinned. Deliberately an exact match on the literal `frc0` rather than "parses to team number 0", so `frc00`/`frc0b` are not quietly swept in. Confirmed with Kanav. |
| 2026-08-01 | **Sentinel handling stays out of `tba_alliance_team_keys`**, applied at four deliberate call sites instead | Filtering inside the shared roster accessor would have been a one-line fix covering all four consumers at once, and was rejected: that helper is documented to return the field unconverted so each caller's own type checking still applies, and hiding the sentinel there would make it invisible to any future check that needs to *see* it — exactly as `-1` stays visible to `_check_unplayed_sentinel`. The four sites (validator identity sets, `normalizer._alliance_roster`, `pipeline._roster_team_keys`, `quality._roster_numbers`) each consult one shared `is_unassigned_team_key()` predicate, mirroring how `TBA_UNPLAYED_ALLIANCE_SCORE` is defined once and interpreted per-consumer. Confirmed with Kanav. |
| 2026-08-01 | **The `frc0` roster-backfill 404 was fixed in the same pass**, not deferred | `pipeline._roster_team_keys` also read `frc0` as a team, so every run of an affected event fetched `/api/v3/team/frc0`, 404'd, and recorded a fresh `extraction_failure` warning. Same sentinel, same per-run re-logging, different module — fixing three of the four sites would have left a known wart behind a fix that claims to close the issue. Confirmed with Kanav. |
| 2026-08-01 | **The live watch's stop condition is "a final exists and no final is unplayed" — chosen on evidence from all 190 official 2024 events, not on intuition** | The intuitive signal, *"every scheduled match has a result"*, is **wrong, and the stored season proves it**: two of the 190 finished events (`2024gagwi`, `2024mdsev`) permanently hold unplayed matches, because the `-1`/`frc0` sentinel rows load with NULL scores and TBA never reissues a finished event's schedule. A watch keyed on that condition would poll those events **forever**. It also false-positives *mid*-event, in the window between the last qualification match and the playoff bracket being published. The finals signal was then checked the same way and holds perfectly: **190/190** events have a played final and **zero** have an unplayed one — so it is neither premature (it waits out a double-elimination `f1m2`/`f1m3`, rather than firing on `f1m1`) nor unreachable (an unneeded `f1m3` is evidently not published in advance). A calendar fallback covers an event that never publishes finals at all. Both signals read canonical columns the poll just loaded, so the stop check costs **zero** API requests. Confirmed with Kanav. |
| 2026-08-01 | **The calendar fallback's grace period cannot be zero** | `events.end_date` is a *local* calendar date, while the check runs on UTC. At a venue west of UTC the event is still running after UTC has rolled over — 7pm Saturday in Houston is already Sunday 00:00 UTC — so `today_utc > end_date` would stop a watch **during Einstein finals**. One day of grace covers every timezone FRC competes in, and the fallback only ever matters for an event with no finals at all, where a day of extra polling is irrelevant. |
| 2026-08-01 | **Statbotics runs on its own 30-minute clock inside the watch, not once per poll** | Extraction requests Statbotics once *per team*, so a 40-team regional is ~40 requests per poll versus TBA's 3 — at a two-minute cadence that is **1,200 requests/hour** to a free community API that explicitly asks callers to be nice to its servers. Decoupling the two clocks (`--statbotics-interval`, default 1800s) drops it to ~80/hour while still refreshing EPA during play, and costs nothing structurally because `sync_event` already accepts `statbotics=None` as a supported TBA-only mode. The watch also reuses `statbotics_probe_failure` to circuit-break a dead Statbotics for the whole run, for the reason `sync_season` already documents: 40 failing lookups per poll, each burning the full retry ladder, would turn a two-minute cadence into minutes of pure timeout. Confirmed with Kanav. |
| 2026-08-01 | **Idle backoff starts after 3 consecutive no-op polls, not the first one** | Backing off immediately looks tidier and is wrong for this workload: a 7-8 minute qualification cycle produces 2-3 polls that land nothing *during perfectly normal play*, so a first-poll backoff would slow detection exactly when the event is live. Waiting for a third consecutive idle poll leaves in-play responsiveness untouched while still walking the interval up to the 600s ceiling overnight — which cuts a 12-hour idle stretch from ~1,080 requests to ~216. The backoff snaps back to the base interval the instant anything lands. |
| 2026-08-01 | **A failed poll is never fatal; only `max_failures` *consecutive* failures end the watch** | TBA being briefly unreachable is a normal condition at a venue, and a watch that dies on the first blip fails at its one job. This mirrors `sync_season`'s existing per-event failure isolation exactly, and rests on the same fact: `sync_event` has already written its `failed` run row and its quality evidence by the time it re-raises, so catching and continuing loses no audit trail. The consecutive cap exists for the opposite failure mode — a mistyped event key 404s on every poll forever — and is the only exit that returns a non-zero status. Verified both ways live: a real watch exits 0, `--watch 2024nosuchevent` exits 1. |
| 2026-08-01 | **`watch_event` holds running totals, not a list of every poll's `SyncResult`** | A watch runs for days at a two-minute cadence, so retaining each result (and every quality issue inside it) would grow unboundedly to duplicate what `pipeline_runs` already records durably — one row per poll, which is the real audit trail. `WatchResult` therefore carries summed `landed`/`loaded`, counts, the latest `EventProgress`, and the stop reason. |
| 2026-08-01 | **`epa_total` resolved: it is EPA at the *end* of the event** — the 2026-07-28 audit's concern is settled, no schema change needed | The audit found Statbotics's bulk CSVs track EPA as a per-event time series (`epa_start`/`epa_pre_playoffs`/`epa_end`/`epa_mean`/`epa_max`) and flagged that `StagingTeamEventStats.epa_total` did not say which value it held. The live v3 API answers it: `epa.stats` exposes only `start`/`pre_elim`/`mean`/`max` — **no `end`** — and top-level `epa.total_points` is distinct from all four for **42/42** teams at 2024casj. So `total_points` *is* the end-of-event value, which is the right semantic for a team-event metric and exactly what §9.1 predicted. The existing mapping was already correct; nothing to change. |
