should be read as a sign-off. When one is written it goes in this section,

The two halves of a `TeamMetrics` are in very different states.

### Scoring metrics — validatable now, pending a focused human pass

`ScoringProfile` is fully populated on real data. `2024casj` holds 42 computed
`team_metrics` rows with real spreads (team 1678: 17/17 matches, average 92.6,
stddev 26.2, consistency 71.7, 4 good / 10 average / 3 bad days), and the
harness prints all of it. Validating this half needs nothing built — only a
human pass against a team whose 2024 season is known well enough to judge the
numbers.

One caveat the harness prints at every site, repeated here so it cannot be
signed off by accident: **`reliability_score` is not yet what its name
promises.** The computed value is the interim
`100 * matches_used / matches_scheduled`, not the intended no-show/DQ measure,
because the canonical schema carries neither no-show nor DQ status
(`data/metrics/schemas.py` documents the gap). It reads 100.0 for every team
whose scheduled matches all have a stored score — which is most of them. It is
a placeholder, and validating it validates nothing.

### Defense/feeding — BLOCKED, and this is the gap that matters

**The database contains zero `scouting_observations` rows.** Not zero for
`2024casj`; zero across every event, all time. Every real team therefore
reports `defense_insufficient_data=True` / `feeding_insufficient_data=True`,
both scores `None`, both counts 0, `contributing_sources` empty.

The consequence is worth stating plainly, because it is easy to miss behind a
green test suite: **the defense/feeding pipeline has never processed a single
real human observation.** Every part of it — M5 validation, M6 normalization,
M7 submission, M8 aggregation, M9 ScoutRadioz import, M10's composition into
`TeamMetrics` — is exercised only by tests and by seeded sentinel data. It is
unvalidated end to end against reality. That pipeline is the *"defense/feeding
scores = directly measured, NOT inferred from point output"* critical
constraint made real, i.e. the feature the constraint exists to protect, so
"works on seeded data" is not a state it should stay in.

Nothing is known to be wrong with it. The seeded verification run behaved
correctly across every case the display has to handle — high agreement, low
agreement (a 4-scout split of 5/2/0/4 producing a 3.0 median at 0.23
agreement), two sources on one team, defense-only observations, a single
observation correctly suppressed by M8's 2-observation minimum, and zero
observations. But that is the pipeline agreeing with data this project
generated for it, which is exactly the kind of self-grading M14 exists to
avoid.

**To unblock:** ingest real scouting data for an event someone attended, via
M7's `submit_human_scout_observation` or M9's `import_scoutradioz_csv`, then
recompute that event and run the harness against it. Until then the
defense/feeding half of M14's sign-off cannot be written, and the feature
should not be trusted in a decision that matters. Tracked in Known Issues.

## M14 — Defense/Feeding Human Validation — DEFENSE SIGN-OFF (2026-08-08, Sven)

**Status: DEFENSE validated and signed off. FEEDING deferred (no data exists).**
This closes the defense half of M14. The feeding half remains open for one
reason only — no feeding observations exist in any available source.

### Event and data checked
- Event: **2026mrcmp** (FIRST Mid-Atlantic District Championship, 2026).
- Source: full ScoutRadioz export, `data/imports/matchscouting_frc11_2026mrcmp_full.csv`
  — 791 rows, 332 rated defense observations after excluding 459 qDefenseQuality=0
  ("played no defense") rows, imported via `scripts/import_2026mrcmp_scouting.py`
  (target_min=1, excluded_values=("0",)).
- 331 observations landed across 66 teams; **58 teams** cleared the 2-observation
  minimum and received a defense_score.

### What was validated
- **Pipeline, end to end, at production volume.** Ingest → normalize → aggregate →
  compute → serve runs on 331 real human observations with correct low-end scaling
  (the target_min rescale fix, commit 75940ae — canonical 0 no longer collapses
  real low ratings; team 10070 went 0.0 → 1.0 on 7 observations).
- **Defense scores corroborated against an independent aggregation.** The computed
  scores were rank-compared (Spearman) against the DCMP team summary's independently
  produced Defense Score:
    - **ρ = 0.79 like-for-like** (both measured as "quality across all rows" from
      the same underlying data) — strong agreement; the aggregation computes the
      quantity it was designed to.
    - ρ = 0.51 against the summary's as-published metric — the gap is a **definition
      difference, not a defect**: the pipeline measures defense *quality when
      defending* (0-rows excluded), the summary measures *quality × volume*
      (0-rows averaged in). Confirmed by reconstructing both statistics from the
      same CSV.
- The DCMP summary is a **human-aggregated reference with expected transcription/
  averaging error** — a corroborating source, not ground truth. The 0.79 is
  therefore a *floor* on real agreement, not a ceiling.

### Caveats (these bound what the metric may be used for)
- **Single-scout dataset. `defense_agreement` is NOT an inter-scout reliability
  signal.** Zero (match, team) pairs were rated by more than one scout. The
  agreement number reflects per-team match-to-match consistency mixed with unknown
  scout-calibration noise. **It must never be used as an observer-reliability
  feature in the ML model.**
- **The served metric is "quality when defending," not "how much a team defended."**
  Excellent-but-rare defenders (e.g. 222, 272, 555) rank high; frequent mediocre
  defenders rank low. [DECISION FOR ALLIANCE SELECTION — see open item below.]

| 2026-08-01 | **The live watch's stop condition is "a final exists and no final is unplayed" — chosen on evidence from all 190 official 2024 events, not on intuition** | The intuitive signal, *"every scheduled match has a result"*, is **wrong, and the stored season proves it**: two of the 190 finished events (`2024gagwi`, `2024mdsev`) permanently hold unplayed matches, because the `-1`/`frc0` sentinel rows load with NULL scores and TBA never reissues a finished event's schedule. | 2026-08-01 | **The calendar fallback's grace period cannot be zero** | `events.end_date` is a *local* calendar date, while the check runs on UTC. One day of grace covers every timezone FRC competes in, and the fallback only ever matters for an event with no finals at all, where a day of extra polling is irrelevant. |
| 2026-08-01 | **Statbotics runs on its own 30-minute clock inside the watch, not once per poll** | Extraction requests Statbotics once *per team*, so a 40-team regional is ~40 requests per poll versus TBA's 3 — at a two-minute cadence that is **1,200 requests/hour** to a free community API that explicitly asks callers to be nice to its servers. Decoupling the two clocks (`--statbotics-interval`, default 1800s) drops it to ~80/hour while still refreshing EPA during play, and costs nothing structurally because `sync_event` already accepts `statbotics=None` as a supported TBA-only mode. The watch also reuses `statbotics_probe_failure` to circuit-break a dead Statbotics for the whole run, for the reason `sync_season` already documents: 40 failing lookups per poll, each burning the full retry ladder, would turn a two-minute cadence into minutes of pure timeout. Confirmed with Kanav. |
| 2026-08-01 | **Idle backoff starts after 3 consecutive no-op polls, not the first one** | Backing off immediately looks tidier and is wrong for this workload: a 7-8 minute qualification cycle produces 2-3 polls that land nothing *during perfectly normal play*, so a first-poll backoff would slow detection exactly when the event is live. Waiting for a third consecutive idle poll leaves in-play responsiveness untouched while still walking the interval up to the 600s ceiling overnight — which cuts a 12-hour idle stretch from ~1,080 requests to ~216. The backoff snaps back to the base interval the instant anything lands. |
| 2026-08-01 | **A failed poll is never fatal; only `max_failures` *consecutive* failures end the watch** | TBA being briefly unreachable is a normal condition at a venue, and a watch that dies on the first blip fails at its one job. This mirrors `sync_season`'s existing per-event failure isolation exactly, and rests on the same fact: `sync_event` has already written its `failed` run row and its quality evidence by the time it re-raises, so catching and continuing loses no audit trail. The consecutive cap exists for the opposite failure mode — a mistyped event key 404s on every poll forever — and is the only exit that returns a non-zero status. Verified both ways live: a real watch exits 0, `--watch 2024nosuchevent` exits 1. |
| 2026-08-01 | **`watch_event` holds running totals, not a list of every poll's `SyncResult`** | A watch runs for days at a two-minute cadence, so retaining each result (and every quality issue inside it) would grow unboundedly to duplicate what `pipeline_runs` already records durably — one row per poll, which is the real audit trail. `WatchResult` therefore carries summed `landed`/`loaded`, counts, the latest `EventProgress`, and the stop reason. |

| 2026-08-02 | **`scouting_observations.raw_payload_id` is `ON DELETE SET NULL`, not `CASCADE`** — deliberately the *other* 0007 precedent | The M2 brief said to follow `canonical_lineage.raw_payload_id` (CASCADE); that was the wrong half of 0007 and was corrected. 0007 actually sets two rules: a row that is **purely a subordinate audit record** cascades, while a **provenance pointer hanging off a row that must outlive it** is SET NULL (`canonical_lineage.pipeline_run_id`, *"a deleted run must not erase the payload→row provenance"*). ## 🔑 Critical Constraints (Do Not Forget)

- Defense/feeding scores = **directly measured**, NOT inferred from point output
- Win probabilities = **unbiased** — AI strategy cannot get inflated odds
- Core engine = **no LLM API calls** — ML / stats / optimization only
- LLM allowed only for: natural-language report generation and explanations
- Real-time updates must sync **during an event** as matches are played — a **real-time-phase target, not a Phase 3 guarantee**: `--watch` keeps the canonical tables current, but `team_metrics` only recomputes on the single-event path, so the metrics the API serves do not move during a watch (`docs/metrics_pipeline.md` §9.9)
