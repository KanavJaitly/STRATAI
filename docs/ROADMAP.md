StratAI — Master Build Checklist
☐ Phase 1 — Foundation
Lock the tech stack (backend language, API framework, PostgreSQL, cache layer, frontend, deployment target) and don't build until it's decided. Set up a shared GitHub repo with folder structure (/api, /data, /ml, /frontend). Design the PostgreSQL schema for teams, matches, events, raw scores, and metrics — leave columns stubbed for metrics not yet calculated. Set up local dev environment running the full stack. Document all decisions in Running Notes.
 Done means: the full stack runs locally, the schema is agreed and committed, and no architectural decision remains open.
☐ Phase 2 — Data Pipeline Note: TODO: Verify live Statbotics API EPA field semantics (confirm canonical mapping for epa_total) once API is stable; update models/tests if needed. 
Build the TBA API client: team data, match results, event rosters, rankings. Build the Statbotics integration: EPA ratings and historical stats. Store raw responses in the database before normalization. Build a normalization layer that maps raw TBA/Statbotics data cleanly into the schema. Build a polling/sync mechanism so data continuously refreshes during a live event — always using the most recent data available. Defer ScoutRadioz (API availability uncertain); leave a clean integration point for it.
 Done means: the pipeline runs against the full 2024 season, the data is manually spot-checked against known real results with no discrepancies, and live-event polling works without manual triggering.
☐ Phase 3 — Team Metrics Engine
Build core statistical metrics as pure functions on match history: average scoring, standard deviation, consistency rating, good-day/average/bad-day performance, and reliability score. Design the data model for defense and feeding scores as directly measured values — never inferred from point output. Build at least one working measurement path: ScoutRadioz pull if available, a human scouting input form, or both. Build API endpoints exposing the full team metrics object.
 Done means: given any team number + event, the system returns a complete metrics object, and defense/feeding scores match what a knowledgeable human scout would say about teams you know personally. If they don't match, the measurement approach isn't done.
☐ Phase 4 — ML Models
Build the team rating/ranking model (start with XGBoost) using team metrics as features; train on historical seasons, validate on a held-out season. Build the win probability model: two 3-robot alliances in, win probability out. Build the alliance synergy scoring function as a weighted combination of role fit, scoring distribution, and defense/feeding coverage. Build the backtesting framework that runs any model against historical seasons and reports accuracy — everything after this phase gets validated through it.
 Done means: the win probability model is calibrated — when it says 60%, that alliance historically wins 58–62% of the time across the backtest — and the ranking model beats a naive baseline (e.g., raw EPA ranking) on the held-out season. If it doesn't beat the baseline, iterate before checking the box.
☐ Phase 5 — Pre-Season & In-Season Intelligence
Build the game-analysis module: ingest new game rules, compare mechanics to historical FRC games, identify likely robot archetypes with strengths, weaknesses, expected success rates, and which will dominate. Build the team capability intake (budget, manufacturing, programming, resources) that outputs a realistic robot ceiling, recommended archetype, and achievable features. Build Week 0/Week 1 meta-tracking: detect emerging meta, underperforming concepts, and design pivot signals from early event data. Build event-specific pre-event analysis: attending team comparison, predicted rankings, likely alliance captains, playoff contenders. Build the in-season learning loop that activates around match 20+: continuously update ratings, detect strategy/meta shifts, and surface recommended adjustments as new data arrives — no manual retraining.
 Done means: the pre-season module can run end-to-end within 5 days of a game reveal (dry-run it against a past season's game reveal to prove it), and mid-season the ratings visibly update as new matches flow in.
☐ Phase 6 — Strategy & Alliance Selection Engines
Build the match strategy engine: given your alliance, opposing alliance, event context, season data, historical data, and coach observations, generate role assignments, defensive assignments, and scoring priorities via optimization — no LLM. Build the coach scenario mode: a human enters a manual strategy and it runs through the same win probability model. Both strategies get honest, purely data-driven odds — if odds are low (12% vs 6%), report them low. Build the alliance selection engine: score every candidate pick using synergy, defense, feeding, reliability, consistency, and role compatibility — optimizing for playoff win probability, not raw scoring. Output ranked pick lists with reasoning plus 3–5 alternative alliance configurations with predicted playoff performance.
 Done means: run alliance selection against a real past event and it identifies most of the actual strong playoff alliances (or has a defensible reason where it differs), and there is verifiably zero mechanism for AI strategies to receive inflated odds — same model, same inputs, for both paths.
☐ Phase 7 — API Layer
Build clean, tested endpoints for: match strategy, win probability, team metrics, rankings, alliance selection, event analysis, and pre-match report data. Write real request/response examples for every endpoint and lock the response shapes before any frontend work.
 Done means: every core feature is callable via API with documented examples, and no endpoint shape changes after frontend work begins.
☐ Phase 8 — Frontend / Dashboard
Build the team profile page (metrics, performance history, charts). Build the match strategy view (AI vs. coach strategy side-by-side with win probabilities and role assignments). Build the alliance selection view (pick list, synergy scores, playoff probability, alternative combos). Build the event dashboard (team list, predicted rankings, playoff contenders). Build the shareable pre-match report view containing exactly: our alliance (role, expected scoring contribution, strengths/weaknesses per robot), opposing alliance (roles, contributions, defensive threats, key risks), and match forecast (predicted flow, critical matchups, key success factors, win probability).
 Done means: every view runs off the real API endpoints, and the pre-match report is complete and shareable with an alliance partner as-is.
☐ Phase 9 — LLM Report Layer (Last, Not Critical Path)
Confirm every prediction, ranking, strategy, and pick list works with zero LLM involvement. Then wire up an LLM API purely as a formatting/explanation layer that turns the engines' structured outputs into readable pre-match briefings. Estimate token cost per event.
 Done means: disconnecting the LLM entirely changes nothing except report readability — no prediction or recommendation is affected — and cost per event is known and minimal.
☐ Phase 10 — Polish, Backtesting, and Hardening
Run the full backtesting suite against the 2022, 2023, and 2024 seasons. Re-validate win probability calibration across all three. Re-validate alliance selection against real playoff outcomes. Re-validate defense/feeding metrics against manual scouting spot-checks. Stress-test real-time sync under simulated live-event match load. Fix anything wrong or biased before calling it launch-ready.
 Done means: all three seasons backtest cleanly, calibration holds across seasons (not just one), and the system survives a simulated event without stale data or crashes.
